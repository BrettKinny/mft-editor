# Upstream status: firmware `20260601` and MFU 2.91

*Research notes from 2026-06-11. This documents what DJ TechTools shipped on
2026-06-01, what it means for mft-editor, and the plan for supporting it.
Status: **investigation planned, not started** — mft-editor currently targets
legacy (2024-era) firmware only.*

## What shipped upstream

On **2026-06-01** DJ TechTools released new firmware for all Midi Fighter
devices plus **Midi Fighter Utility 2.91** (patched 2.91.1 on 2026-06-05),
their first utility release in ~2 years.

- Blog: <https://djtechtools.com/2026/06/01/midi-fighter-utility-2-91-is-out-our-biggest-update-in-years/>
- Forum thread: <https://forum.djtechtools.com/t/midi-fighter-utility-2-91-released/154813>

### Twister firmware `20260601` changelog (protocol-relevant items bolded)

- Device reports a **unique serial number** ("groundwork" per DJTT)
- **Switchable color palette** — legacy palette or MF64 palette, selected via MFU
- **8 Banks alternative firmware** variant (step sequencer disabled in that build)
- **RGB recalibration**; **white** now renders as true white (was lavender)
- **Configurable shift encoder channel (per encoder)**
- **Configurable animation channels (global)**
- **New encoder action: "reset encoder value (127)"**
- **New side-button action: "Bank Select"**
- **Shift Page A/B side-button actions now exist as both toggle and momentary**
- **New indicator type: "Spread"** (center-out symmetric; groundwork for an
  upcoming Mackie-style "native mode")
- **Bank change animations** (can be disabled in MFU Global tab)
- **Display sleep timer + sleep animation (RGB wave or off)**
- MFU shows detent state/color; no longer moves detented encoders to 0 on load

### MFU 2.91 (editor) highlights

Multi-device support with nicknames, bidirectional bank sync, decoded SysEx
logging (including firmware date), experimental undo/redo, bootloader
detection/recovery, Qt 6.8.3, light/dark themes, multi-encoder select.
**MFU reads the firmware date and hides settings the connected firmware
doesn't support; units on 2026 firmware require MFU 2.91+.**

Announced for later in 2026: profile manager for multiple `.mfs` files,
Apple Silicon universal binary, native mode.

### The catch: no published spec

The official open-source firmware repo
([DJ-TechTools/Midi_Fighter_Twister_Open_Source](https://github.com/DJ-TechTools/Midi_Fighter_Twister_Open_Source))
was **last pushed 2024-04-19** — the `20260601` source is not public, and as of
2026-06-11 nobody has published reverse-engineered docs of the new SysEx
fields. DJTT made no statement about publishing it. Notable unmerged community
PRs there: #25 "Add native mode" (2025-06), #24 CMake avr-gcc toolchain.

### Field reports worth knowing (from the 2.91 forum thread)

- Config **import corruption**: colors and side-button assignments altered on
  import — consistent with palette remapping between firmware generations.
- Side buttons remapping from Prev/Next Bank to Shift pages after update.
- Bank-change animation caused audio stutter in Traktor for one user.
- New "Midi Fighter Twister Rescue" Zendesk article (bootloader recovery):
  <https://techtools.zendesk.com/hc/en-us/articles/37721503876109>

## Findings from the legacy firmware source (verified 2026-06-11)

Read from the 2024 open-source firmware (`sysex.c`, `config.c`, `encoders.c`):

1. **Identity handshake exists and we don't use it.** The firmware answers the
   standard MIDI Device Identity Request (`F0 7E 7F 06 01 F7`) with
   manufacturer, family, model, and the **firmware date** (year/month/day) —
   exactly what MFU 2.91 uses to gate features. mft-editor hardcodes
   `firmware_version = "Unknown"` (`mft_editor/midi/device.py`) and never asks.
   The commented-out serial-number bytes in that handler (`sysex.c`) are very
   likely what the 2026 firmware re-enabled.

2. **Push is tag-sparse.** On an encoder push the firmware initialises all
   config bytes to `0x80` ("invalid"), fills in only the tags present in the
   message, and `save_encoder_config()` skips `0x80` bytes when writing
   EEPROM (`config.c` `sysExCmdBulkXfer`, `encoders.c:324`). Global config
   push is likewise per-tag. **Omitted fields are preserved in EEPROM.** So
   pushing only our 15 known tags should not wipe new-firmware settings *in
   storage* — assuming the 2026 firmware kept these semantics
   (assumed, not guaranteed).

3. **The RAM-image quirk.** `save_encoder_config()` copies the *entire*
   incoming struct — including the `0x80` invalid markers — into the live RAM
   config (`encoders.c:328`) before the sparse EEPROM write. Fields omitted
   from a push are therefore corrupted in RAM until the config is reloaded
   from EEPROM (e.g. bank switch / reboot). This is the same bug family as our
   earlier "multi-part SysEx corrupting encoder RAM" fix. Consequence: on 2026
   firmware, a push that omits the new tags could leave the device visibly
   misbehaving even though EEPROM is intact. Unknown whether the 2026
   "code optimization" changed this.

4. **Unknown tags are currently dropped on pull.** Both protocol
   implementations (`mft_editor/midi/sysex.py`, `web/packages/core/src/sysex.ts`)
   ignore tags outside the 15 known encoder fields / 12 global fields. On 2026
   firmware, new settings pulled from the device are silently discarded — they
   never reach the model or saved presets.

## Plan

### Stage 1 — compatibility-first (before editing any new feature)

The contract for a device on 2026 firmware: **warn, allow full editing of
known fields, and never destroy what we don't understand.**

1. Send a Device Identity Request on connect; surface the firmware date in
   both UIs and use it to detect 2026 firmware.
2. Show a notice on 2026 firmware: "new firmware detected — its new settings
   are not yet editable here."
3. Preserve unknown tags as opaque bytes through the whole round trip:
   pull → model → preset file → push (replayed alongside known tags). Sparse
   push makes the replay safe; replaying also sidesteps the RAM-image quirk
   by never omitting fields the device knows. Add fixtures so the Python and
   TypeScript layers stay byte-exact.
4. UI rule for out-of-range enum *values* (e.g. the new "Spread" indicator
   type): display as "Unknown (value N)" and leave untouched unless the user
   explicitly changes it. Never coerce silently.

### Stage 2 — bench reverse-engineering (deferred; needs hardware time)

Goal: derive the `20260601` SysEx encoding empirically, since no source or
spec is public.

0. **Before updating anything:** with the device still on legacy firmware,
   pull and archive a full config dump (mft-editor preset + raw SysEx capture)
   as the cross-firmware baseline.
1. Install MFU 2.91.1; update one Twister to `20260601` (keep a rescue path:
   the new bootloader-recovery flow + the Twister Rescue article).
2. Capture MFU ↔ device traffic on Linux via `amidi -p hw:X -d`, `aseqdump`,
   or Wireshark usbmon. Confirm the identity exchange and whether MFU sends
   anything new during its handshake (capability query, palette select).
3. Toggle exactly one new setting at a time in MFU and diff the SysEx:
   shift channel, reset-to-127 action, Spread indicator, Bank Select,
   toggle/momentary Shift Page, animation channels, sleep timer/animation,
   bank-change animation, palette switch. Record tag numbers and value
   encodings for each.
4. Pull the same config back and diff against the push — confirms which
   fields live where and whether pull echoes everything.
5. Verify 2026 push semantics: is push still tag-sparse? Does the RAM-image
   quirk persist? (Push a partial config, observe live behavior vs after a
   bank switch.)
6. Check the 8-bank variant: does the encoder tag space extend to 128
   (`bank*16 + encoder + 1`), and what does pull return for banks 5–8?
7. Compare legacy vs MF64 palette mappings against our `color_map` tables;
   document the recalibrated RGB values (white especially).
8. Each decoded field graduates from "opaque tag" (Stage 1) to a named field
   in both protocol layers, with a shared fixture.

### Stage 3 — new-feature editing

Expose the decoded fields in both UIs, gated on firmware date the same way
MFU 2.91 gates them. Out of scope until Stage 2 lands.
